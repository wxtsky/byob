# B v0.2 稳定性设计：Cancel + CDP Fallback + Wake

> **状态**：草案，待用户审核
> **日期**：2026-04-25
> **关联**：v0.1 整体设计 [`2026-04-25-byob-design.md`](2026-04-25-byob-design.md)
> **目标版本**：v0.2

## 1. 概述

把 byob 从 "11 个工具能跑通" 升级到 "11 个工具能可靠地跑通"。本 spec 不加新工具，三项纯内部修复：

| 项 | 解决什么 |
|---|---|
| **Cancel/Abort 全链** | mcp-client Ctrl+C 时，mcp-server → bridge → extension → CDP 整链干净停下，不留 zombie session |
| **CDP fallback to chrome.scripting** | `browser_eval` 在 CDP attach 失败时（DevTools 占用、扩展刚 reload）自动降级到 `chrome.scripting.executeScript` |
| **Wake/sleep 检测** | macOS 合盖唤醒后 CDP state 不一致，自动检测并 reset |

iframe 跨 frame 支持已拆到独立 D spec（属于功能扩展，不是稳定性）。

## 2. 动机

HANDOFF 已知小坑里直接相关的：

- "`browser_eval` 不传 tabId 时偶发 `cdp_attach_failed`" — activeTabId 跟 CDP attach race（Cancel 全链 + CDP fallback 都覆盖）
- "首次 reload 扩展后跑 `browser_eval` 第一次会失败"（CDP 刚 detach）— CDP fallback 直接覆盖
- 用户实际工作流：mcp-client 长跑工具（fullPage 截图、`browser_read_markdown` 大 page、未来的 `record_network`）需要能可靠中断
- macOS 用户合盖唤醒（高频）后 CDP state 不可信，需要自动恢复

## 3. 非目标

- **不做 partial result 上报**（"已截 30/100"）。Cancel 是 abort，不是 streaming。
- **不做自动重试**。abort 后由 client 决定重试与否。
- **不做 iframe 支持**（D spec）。
- **不做现有 11 个工具的 UX 优化**（`screenshot` 默认开新 tab 之类）。
- **不改现有协议帧的 wire format**，仅追加字段（向后兼容）。

## 4. Cancel/Abort 全链

### 4.1 信号链路

```
mcp-client → MCP notifications/cancelled (requestId)
mcp-server → catches notification
           → POST bridge /cancel {requestId}
           → 同时 abort fetch(undici Agent) 的 in-flight HTTP request
bridge IPC server → looks up in-flight map[requestId]
                  → calls AbortController.abort()
                  → sends NM 帧 {type:'cancel', requestId} 给 extension
extension SW → background.ts dispatch cancel
             → looks up handler in-flight map[requestId]
             → calls AbortController.abort()
handler → all await sites observe AbortSignal
        → on abort: detach CDP / clear timers / throw 'aborted'
```

### 4.2 协议改动

#### Bridge IPC HTTP 现有：
```
POST / { command, params }   →   { ok: true, data } | { ok: false, error }
```

#### 改为：
```
POST / { command, params, requestId }   →   同上（不变）
POST /cancel { requestId }              →   { ok: true }
```

`requestId` 由 mcp-server 生成（uuid v4）。bridge 用作 in-flight map 的 key。

#### NM 帧追加：
现有：
```
{ type: 'request', id, command, params }
{ type: 'result', id, ok, data?, error? }
```

新增：
```
{ type: 'cancel', id }   ← bridge → extension，告诉 extension 取消 id 对应的 in-flight handler
```

`id` 沿用现有 NM 帧的 id，是 bridge 内部为每个 NM request 生成的，跟 `requestId` 一一对应（bridge 内部映射）。

### 4.3 实现要点

**mcp-server 端**：
- `bridge-client.ts` 每次发请求生成 `requestId = crypto.randomUUID()`
- 发请求时附带 `AbortSignal`（来自 MCP SDK 的 cancel handler）
- AbortSignal 触发时同时 `undici` abort + POST `/cancel`

**bridge 端**：
- `ipc-server.ts` 维护 `inFlight: Map<requestId, { nmId: number, abort: AbortController }>`
- 收到 cancel：abort + 发 NM cancel 帧
- 收到 NM result（无论 ok/error）：从 map 删除
- HTTP request abort 也触发 `/cancel` 等价逻辑（防止 client 端 socket 断连后 extension 还在跑）

**extension SW 端**：
- `background.ts` 维护 `inFlight: Map<nmId, AbortController>`
- handler 入参追加 `signal: AbortSignal`
- 收到 NM cancel 帧：`AbortController.abort()` + 从 map 删
- handler 跑完（或抛错）从 map 删
- 抛错时如果 signal aborted，error type 是 `aborted` 而不是原始 error

**handler 改造**：
- 所有 long-running 操作（`waitForLoad`、`Runtime.evaluate`、`Page.captureScreenshot`、`MutationObserver` 等）：
  - 包装成 cancellable promise（`Promise.race([op, abortPromise(signal)])`）
  - abort 时清理：detach CDP、clear timer、close port
- `cdp.ts attach()` 加 signal 参数；attach 中途 abort 立即 detach 并 throw

### 4.4 边界

- **handler 已经返回了 result，cancel 才到达**：丢弃 cancel（map 已删）
- **多次 cancel 同一 requestId**：幂等，第二次 no-op
- **cancel 一个不存在的 requestId**：返 200 ok，记 warn log（可能是竞态）
- **bridge 进程在 cancel 到达前 crash**：mcp-server 自然超时，重启 bridge

## 5. CDP fallback to chrome.scripting

### 5.1 范围

只覆盖 `browser_eval`。其它工具不依赖 `Runtime.evaluate`：
- `read` / `screenshot` 用 CDP 但替代不到 chrome.scripting（截图必须 `Page.captureScreenshot`）。这两个失败就老老实实抛错。
- `click` / `type` 用 CDP `Input.dispatch*`，chrome.scripting 模拟事件不等价（不触发某些 framework 的 listener）。失败抛错。
- `cookies` 走 `chrome.cookies` 不依赖 CDP。
- `eval` 是唯一既能用 CDP 又能用 chrome.scripting 的工具。

### 5.2 实现

`packages/extension/lib/handlers/eval.ts`：

```ts
export async function handleEval(params, signal) {
  // ... 解析 tab ...
  let session;
  try {
    session = await cdp.attach(tabId, { signal });
    const result = await session.send('Runtime.evaluate', {
      expression: code,
      awaitPromise: true,
      returnByValue: true,
    });
    return { value: result.result.value, fallbackUsed: false };
  } catch (e) {
    if (e instanceof CDPAttachError) {
      // 降级
      const [out] = await chrome.scripting.executeScript({
        target: { tabId },
        world: 'MAIN',
        func: new Function('code', 'return eval(code)'),
        args: [code],
      });
      return { value: out.result, fallbackUsed: true };
    }
    throw e;
  } finally {
    session?.detach();
  }
}
```

### 5.3 语义差异（用户必须知道）

| 维度 | CDP `Runtime.evaluate` | chrome.scripting fallback |
|---|---|---|
| RemoteObject (类型/className/objectId) | ✓ | ✗（只返 value） |
| awaitPromise | 显式参数 | 自动 await async function 返回值 |
| 错误堆栈 | 详细 lineno/colno | 简化 |
| 跨 origin frame | 看主 frame | 看主 frame |
| 大对象序列化 | 可深度控制 | structured clone 一次 |

### 5.4 接口变化

`browser_eval` 输出新增字段：

```ts
{
  value: any;
  fallbackUsed: boolean;       // 新增
  // _meta: { fallbackUsed: true } 也通过 MCP 元数据透出
}
```

mcp-server 收到 `fallbackUsed: true` 时在 MCP response 的 `_meta` 加同名字段，client 可见。

## 6. Wake/sleep 检测

### 6.1 检测机制

两路：

**路 1：Heartbeat 跳跃**
```ts
let lastTickAt = Date.now();
chrome.alarms.create('wake-watch', { periodInMinutes: 1 });
chrome.alarms.onAlarm.addListener((alarm) => {
  if (alarm.name !== 'wake-watch') return;
  const now = Date.now();
  const elapsed = now - lastTickAt;
  lastTickAt = now;
  if (elapsed > 90 * 1000) {        // 应该 60s，跳了 ≥ 1.5x 算 wake
    triggerWakeRecovery();
  }
});
```

**路 2：idle 状态变化**
```ts
chrome.idle.setDetectionInterval(60);
let lastIdleState: chrome.idle.IdleState = 'active';
chrome.idle.onStateChanged.addListener((state) => {
  // 从 idle / locked 回到 active：可能刚 wake
  if ((lastIdleState === 'idle' || lastIdleState === 'locked') && state === 'active') {
    triggerWakeRecovery();
  }
  lastIdleState = state;
});
```

两路是冗余的（任一触发都行）。alarm 路覆盖 SW 持续运行场景；idle 路覆盖系统层信号。重复触发 recovery 无害（detach 是幂等的）。

### 6.2 Recovery

```ts
async function triggerWakeRecovery() {
  console.warn('[wake-watch] resetting CDP state');
  // 1. abort 所有 in-flight handler（让它们快速失败而不是 hang）
  for (const [nmId, controller] of inFlight) {
    controller.abort('aborted_due_to_wake');
  }
  // 2. detach 所有 CDP session（state 不可信）
  await cdp.detachAll();
  // 3. 不主动 reattach：下次 handler 调用时按需新 attach
  // 4. notify bridge 让它知道（用于诊断 log）
  port.postMessage({ type: 'wake_recovery' });
}
```

### 6.3 文件位置

- `packages/extension/lib/wake-watch.ts`（新）
- `packages/extension/entrypoints/background.ts` 启动时调 `wakeWatch.start()`

## 8. 错误处理

| 场景 | error code | 触发位置 |
|---|---|---|
| 用户 cancel（mcp Ctrl+C 或 client abort） | `aborted` | handler 检测 signal |
| Wake 期间 in-flight 调用被强制中止 | `aborted_due_to_wake` | wake-watch trigger |
| CDP attach 失败但 fallback 也失败 | `cdp_attach_failed`（现有） | eval handler |
| cancel 一个不存在 requestId | 返 200 ok（不算错） | bridge |
| handler 收到 abort 但 detach CDP 失败 | 静默 warn log | cdp.ts |

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| handler 改造遗漏某处 await，cancel 时 hang | 用户感觉 cancel 没生效 | 列 checklist 逐 handler 检查；Cancel e2e 跑遍所有工具 |
| chrome.alarms 在 SW 被 evict 后不触发 | wake-watch 路 1 失效 | 路 2 (idle) 兜底；SW 复活时立即 sync 一次 timestamp |
| Cancel 信号到达时 CDP detach 自身报错 | recovery 不彻底 | detach 失败时 catch + warn，不阻塞 abort 流程 |
| chrome.scripting fallback 跑 `eval(code)` 无 stack trace 时 client 调试困难 | DX 差 | 在 fallback 路径捕获 error 并附 `// fallback used` 提示 |
| 多个 in-flight 请求时 cancel 一个误 abort 别的 | 致命 | requestId/nmId 全程精确传递；不复用 controller |

## 11. 不在范围（v0.3+）

- 部分进度上报（partial result streaming）
- 自动重试 abort 后失败的请求
- iframe 跨 frame 支持（→ D spec）
- bridge 进程崩溃后的自动恢复
- 多 mcp-client 并发（每个 client 自己 cancel 自己）
